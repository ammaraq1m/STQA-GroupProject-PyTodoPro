# PyTodo Pro test strategy

| Approach | Objective, techniques and tools | Priority and limits |
| --- | --- | --- |
| Black-box | Week 1 partitions usernames, passwords, titles, dates, completion timestamps and pagination. Boundary analysis uses adjacent values such as 7/8/9 characters and exact date/time cutoffs. Compare documented oracles with pytest/helper results or Flask test-client responses. Later workflow suites verify state transitions and combined conditions. | Lead with account creation, invalid input, private-task access and stored-state effects. Week 1 evidence supports EP/BVA, with no standalone decision-table or manual execution evidence. Historical scripts are missing. |
| White-box | Week 2 examines control flow, branch outcomes, data dependencies and short-circuit behavior for four pure helpers. Use pytest, deterministic dates and Coverage.py statement/branch measurement. | Target validation and dashboard logic with known boundary risk. Coverage was 31/31 statements and 18/18 measured branches for helpers.py. Routes, exhaustive paths and Boolean combinations have no equivalent measured coverage. |
| GUI | Week 3 Playwright checks navigation, forms, messages, task lifecycle, delete confirmation and shared visual treatment. Preserve DOM measurements and screenshots. | Prioritize account and task workflows and required-field behavior. Scripted checks cover specified checkpoints and configurations. Historical manual checklists remain pending. |
| Compatibility | Week 3 varies Chromium, Firefox and WebKit by viewport and interaction profile. The device extension repeats core workflows and measures task/dashboard width in eight profile/orientation contexts. | Prioritize small-screen task access and desktop consistency. Browser engines and emulated device descriptors provide profile evidence. Native Safari, real devices, OS controls and rotation remain outstanding. |
| Usability | Week 3 scripts observe first-use message, creation feedback, current-page cue, cancellation and validation. Use Playwright and screenshots to capture what appears and where. | Start with discoverability and recovery for core workflows. Observed UI gaps require consented participant work to assess comprehension, efficiency or user impact. |
| Accessibility | Week 3 uses axe-core across seven page states and Playwright for keyboard traversal, focus, semantic landmarks, reflow, simulated resizing and toggle naming. | Prioritize control names, keyboard usability and narrow layouts. Selected WCAG 2.2 A/AA checks and an incomplete contrast result leave manual inspection, native text zoom and screen-reader verification pending. |
| Web and REST API | Week 4 uses Chromium browser flows and Flask test-client pytest. Assert status, response shape, redirects, session changes, persistence and absence of writes. Compare API/browser state using shared-cookie Playwright contexts. | Prioritize API contracts, validation, private task access and write atomicity. Browser constraint checks cover one layer. SQLite/readback assertions expose server failures. Core contracts are sampled with synthetic users. |
| Security | Week 5 uses STRIDE to derive targeted defensive checks for auth, ownership, cookie metadata, credential storage, input handling and source/configuration controls. Use Flask test-client assertions and source/schema inspection. | Prioritize safe parameter binding, owner scope and managed signing configuration, then CSRF, cookies, audit and validation. Runtime adversarial cases and deployment TLS are deferred. Source evidence establishes the sampled implementation weakness. |
| Performance | Week 5 uses Locust, CSV, psutil and Matplotlib for staged authenticated GETs at 1, 5, 10 and 25 users. Compare latency, throughput, errors and resource samples under controlled pacing. | Read-heavy task and dashboard routes come first. Short loopback runs with colocated generator, small fixtures and development server establish an observed baseline. Production load, long duration, writes and saturation are outside this measurement. |
| Automation and regression | Week 6 selects checks by repetition, stability, criticality and ability to detect regressions. Run reused pytest API/security and Playwright flows with six new Flask cases. Record the initial harness failure and final run separately. | Prioritize authentication, ownership, validation and task integrity. Compare to original verdicts and preserve manual trace links. Focused Chromium regression excludes broad browser/axe, physical-device, participant and load reruns. |

Where expectations conflict, use the README and helper specifications for documented behavior and label source-derived acceptance rules as inferred. Keep the original test oracle and outcome when reporting historical results. For new confirmation, pair the original failing condition with a passing control and verify persisted state when applicable. Resolve trace and status changes through the [RTM](Requirements%20Traceability%20Matrix.csv), [execution history](Execution%20History.csv) and [defect register](Master%20Defect%20Register.csv).
